A pedagogic static recompiler · Sega Genesis / Mega Drive

ROM in.Native game out

gase-recomp reads the Motorola 68000 machine code of a cartridge you own and rewrites it, ahead of time, as portable C that compiles natively for desktop, Android and iOS. This page is the making-of: every step, explained so you can build one yourself.

01

Chapter 01 · The pitch

Three steps, zero game data

An emulator pretends to be a Mega Drive. gase-recomp does something different: it translates the game itself into a C program, once, before it ever runs. What you get is a regular native executable — debuggable, profilable, portable.

The tool is deliberately small and heavily commented. It is not trying to be the fastest or the most compatible recompiler out there; it is trying to be the one you can read from end to end in a weekend and then reuse the ideas for another CPU.

  1. STEP 01

    Bring your ROM

    A dump of a cartridge you own: .bin, .md, .gen or interleaved .smd. The loader validates the header and the checksum.

  2. STEP 02

    Choose a platform

    The same generated C feeds three thin shells. Pick where the game should live.

    • Desktop
    • Android
    • iOS
  3. STEP 03

    Recompile

    gase disassembles, analyses, emits C and a build project. Your usual compiler does the rest.

Legal

Bring a ROM you own. gase-recomp ships no game data, no BIOS and no copyrighted assets — only the tool and a hand-written test ROM.

The generated C is a derivative of the game you fed it: keep it for yourself, do not redistribute it.

02

Chapter 02 · Strategy

Why static recompilation?

There are three ways to run old software on new hardware. They differ in one question: when does the old machine code get understood?

Emulation

At runtime, every instruction

An interpreter (or a JIT) fetches, decodes and executes each 68000 instruction while the game runs. Extremely general — self-modifying code, anything goes — but the work is repeated forever, and the program stays a black box.

Effort
Output
A virtual machine

Decompilation

By hand, over years

Humans rewrite the game in C, function by function, until it compiles back to a byte-identical ROM. The result is beautiful, readable source — and it costs thousands of hours per game.

Effort
Output
Human-quality source

Static recomp

Ahead of time, by a tool

A program translates the machine code into C mechanically, once. The CPU disappears into C; the hardware (video, sound, timers) is still emulated by a runtime library. You get native speed and a real program — without hand-writing it.

Effort
Output
Native, ugly but honest C

Static recompilation is not new. Projects such as N64Recomp (Nintendo 64) and XenonRecomp (Xbox 360), and many earlier experiments, showed that the approach scales to real games. gase-recomp applies the same idea to a much simpler machine — which is exactly why it makes a good classroom.

The hard parts are always the same, whatever the CPU: knowing where the code is, handling jumps you cannot predict, and keeping time consistent with hardware that expects interrupts at precise moments. The rest of this page tackles them one by one.

03

Chapter 03 · Loader

Anatomy of a Genesis ROM

A cartridge is just the bytes the CPU sees at address $000000. Learn to read its first 512 bytes and you know where every game begins.

The Mega Drive's main CPU is a Motorola 68000 at about 7.67 MHz: eight 32-bit data registers d0–d7, eight address registers a0–a7 (a7 is the stack pointer), a 24-bit address bus, and — important for every byte you will ever read — big-endian storage: the most significant byte comes first.

The exception vector table

The ROM opens with a table of 32-bit addresses. On power-up the 68000 loads its stack pointer from $000000 and its program counter from $000004. Interrupts and traps jump through the other entries. For a recompiler, this table is gold: it is the list of places where execution is guaranteed to start.

The Sega header at $100

Right after the vectors comes a fixed-layout ASCII header. The console name field must read SEGA MEGA DRIVE or SEGA GENESIS — later consoles' TMSS boot code actually refuses cartridges without SEGA there.

The checksum is a plain 16-bit sum of every big-endian word from $200 to the end of the ROM. It is a sanity check, not a security feature — but it tells you immediately whether your dump is intact.

Undoing the SMD interleave

Old copier devices (the "Super Magic Drive") saved ROMs in a strange layout: a 512-byte header, then 16 KiB blocks where the first 8 KiB hold all the odd bytes and the next 8 KiB all the even bytes. The loader detects it and weaves the bytes back into a flat image, so nothing downstream ever has to care.

Generic lesson: normalise inputs at the very edge of your pipeline. Every later stage assumes one canonical, flat, big-endian image.

Chapter 04 · Decoder

Reading 68000, one word at a time

Every 68000 instruction starts with one 16-bit opcode word. Its top four bits — the "line" — tell you which family you are in; the rest are packed fields.

Line 0 holds immediate operations and bit manipulation, lines 1–3 are MOVE (byte, long, word — yes, in that order), 4 is a grab bag (LEA, JSR, RTS, CLR…), 6 is branches, 7 is MOVEQ, 8/9/B/C/D are arithmetic and logic, E is shifts and rotates. Lines A and F are unassigned and trap.

Try it: pick an instruction and hover the fields.

000002043080  move.w d0,(a0)

00 · 11 (word) · 000 (dest reg) · 010 (dest mode (An)) · 000 (src mode Dn) · 000 (src reg).

Effective addressing modes

Most instructions name their operands with a 6-bit effective address: 3 bits of mode, 3 bits of register. Mode 7 is an escape hatch whose register field selects the "special" modes. Some modes need extension words after the opcode — which is why instruction length varies from 2 to 10 bytes, and why you cannot decode a 68000 program by just stepping two bytes at a time.

The code-versus-data problem

Here is the catch that shapes the whole project. A ROM is a soup of code, graphics, music, level maps and lookup tables, with nothing marking which is which. A tile of pixels decodes happily into nonsense instructions. A linear sweep from $200 to the end would "disassemble" megabytes of art.

So the decoder never chooses where to look. It is a pure function — decode(rom, address) → instruction — and the decision of which addresses are code belongs to the next stage.

05

Chapter 05 · Analysis

Finding the code by following it

If we cannot tell code from data by looking, we tell it by following: start where the CPU is guaranteed to start, and go wherever it can go.

This is recursive descent. The work list is seeded with the reset vector, the interrupt vectors and the TRAP vectors. For each entry, the analyser decodes instructions one after the other, and at each branch it adds the target(s) to the list. A function is an entry point plus every instruction reachable from it through branches (BRA, Bcc, DBcc, JMP to a known label). A call — BSR or JSR — does not extend the current function: it discovers a new one.

The wall: indirect jumps

Games love jump tables. A state machine reads an index, scales it, loads an address from a table and does jmp (a0). The analyser sees a0 but has no idea what it will hold at runtime. Some patterns can be pattern-matched (a d8(PC,Xn) table right after the jump, for instance), but in general this cannot be solved statically — it is a cousin of the halting problem.

gase-recomp does not pretend otherwise. It turns the problem into a workflow, which is the single most important idea to take away from this page:

  1. Recompile what you can see.Recursive descent from the vectors, plus any entry list you provide.
  2. Run the game.Every indirect jump goes through a dispatcher that looks the target up in a table of known functions.
  3. Log what is missing.An unknown target is written to gase_missing.txt, with the instruction that jumped there.
  4. Feed it back.Re-run gase recomp … --entries gase_missing.txt. Coverage grows with each play session, until it converges.

Static analysis proposes, the running program disposes. Every serious recompiler ends up with some version of this loop.

06

Chapter 06 · Codegen

Every instruction becomes a little C

The code generator is almost boring, on purpose: each 68000 instruction is replaced by a small block of C that does exactly what the CPU would have done, then charges the right number of cycles.

D(n) and A(n) are the emulated registers, W16 writes a big-endian word through the memory bus, op_logic sets the N and Z flags and clears V and C exactly as MOVE does, and CYC(8) adds the instruction's cycle cost to the clock. The original address and disassembly stay in a comment, so the output remains a readable map back to the ROM.

The CPU is a struct

The machine state is a plain C struct. Flags are stored unpacked — one byte each — because testing gase_cpu.z is much cheaper than masking a status register on every branch; the real SR is only rebuilt when the game reads it.

Flags come from tiny helpers — op_add, op_sub, op_logic… — declared static inline. The C compiler inlines them, and when a flag is overwritten before anyone reads it, the optimiser simply deletes the dead computation. You write the obvious thing and let the compiler make it fast.

Branches, calls and returns

Inside a function, a branch is a goto to a label named after its address. A call — BSR/JSR — pushes the 68000 return address on the emulated stack, exactly like the real CPU, and then makes a real C call. RTS pops the address into gase_cpu.pc and returns.

Why check gase_cpu.pc after the call? Because 68000 code is free to cheat: a routine can drop its return address and push another one, or a game can switch threads by swapping stacks. If the address that came back is not the one we expected, the C call stack no longer matches the 68000 stack. The function then unwinds to a top-level trampoline, which looks up the real target in the dispatch table and jumps there. When that target is in the middle of a function — just after a call site — the function's resume points (a small switch at its entry) let it be re-entered right at that label.

Generic lesson: map the source machine's control flow onto the host's whenever it is safe, and keep a slow but correct escape hatch for when it is not.

Chapter 07 · Runtime

The CPU is gone. The console is not.

Recompiled code still writes to $C00000 expecting a video chip to be there. The runtime is a small C library that plays the role of everything that is not the 68000.

  1. $000000Cartridge ROM — up to 4 MiBRead directly from a byte array; inlined fast path.
  2. $400000Unused / expansion
  3. $A00000Z80 address space8 KiB sound RAM and the YM2612, shared with the sound CPU.
  4. $A10000I/OVersion register, controller ports, Z80 bus request ($A11100), TMSS ($A14000).
  5. $C00000VDP + PSG portsData port, control port, H/V counter; the PSG lives at $C00011.
  6. $FF0000Work RAM — 64 KiBMirrored from $E00000. Inlined fast path.

The video display processor

The VDP owns 64 KiB of VRAM holding 8×8 tiles and the maps that arrange them into two scrolling planes, A and B, plus a fixed window plane and up to 80 sprites. Colours live in CRAM: four palettes of sixteen 9-bit colours (that is why every colour on this page is a legal Mega Drive colour). Games feed it through a two-word command protocol on the control port and bulk-copy data with DMA. gase renders one scanline at a time, so mid-frame tricks — changing scroll or palette from an HBlank interrupt — keep working.

Sound starts with the SN76489 PSG: three square-wave channels and one noise channel. Controllers are read through the I/O ports with the classic TH-line multiplexing.

Interrupts in an ahead-of-time world

Here is the subtle part. An interpreter can check for interrupts between any two instructions. Our recompiled code runs straight C — so who interrupts it? Answer: cycles and poll points.

VBLANK · LINES 224–261
IRQ 6
Count
Every block starts with CYC(n). About 488 68000 cycles make one NTSC scanline; 262 lines make a frame.
Poll
On every backward branch — every loop — the generated code calls POLL(addr). It is one compare in the common case.
Fire
When a scanline has elapsed, the scheduler runs the VDP for that line. At line 224 it raises the level 6 VBlank interrupt: push PC and SR, call the handler from the vector at $78, resume at the loop head on RTE.

Since every loop polls, and straight-line code is short, an interrupt is never late by more than a few dozen cycles — well under a scanline. That is the trick that lets a program compiled ahead of time still behave like it lives inside a console.

Chapter 08 · Shells

One runtime, three shells

Everything above is portable C99 with no OS calls. The only platform-specific code is a thin shell built on SDL2: a window, a texture, an audio callback, input.

Desktop

CMake · Linux / macOS / Windows

The generated directory is a CMake project. Configure, build, run — keyboard and gamepads through SDL's game controller API.

Android

Gradle · NDK · SDL2 Java activity

A Gradle project wraps SDL2's SDLActivity; the C is built by the NDK. Your ROM is packed into the APK's assets — for your own device only.

iOS

CMake → Xcode

CMake generates an Xcode project; the ROM goes into the app bundle. Sign it with your own developer account and side-load it on your phone.

On phones, the shell draws on-screen touch controls — D-pad, A/B/C and Start — as a translucent overlay, mapped to the same controller state a real pad would write.

info prints the header, vectors and checksum status. recomp writes the C sources, the runtime and a build project for the chosen platform.

Chapter 09 · Verification

Trust, but diff

A recompiler is wrong in silent ways: one flag computed incorrectly and a game takes the wrong branch ten minutes later. You cannot debug that by playing. You need a referee.

The referee is Musashi, a mature and widely used 68000 emulator written in C. The technique is differential testing: generate random but valid instruction sequences, run them through both Musashi and gase's recompiled C from the same starting state, and compare everything afterwards.

Generate

Random opcodes, operands and sizes, a random register file, a few random bytes of RAM. Seeded, so every failure is reproducible.

Reference

Musashi interprets the sequence.

Under test

gase recompiles it to C, which is compiled and run.

Compare

d0–d7, a0–a7, X N Z V C, SR, a CRC32 of the 64 KiB of RAM (exception stack frames included). Any mismatch prints the seed and the instruction.

Random tests find the bugs you did not imagine. For the ones you did, there is a small hand-assembled test ROM: a real cartridge image, written from scratch for the project, that exercises the vectors, the VDP, interrupts and jump tables — and is legal to ship. Everything runs on GitHub Actions for every pull request: unit tests, the differential suite, and a full recompile-and-build of the test ROM.

Generic lesson: if a mature reference implementation exists for your CPU, your first test harness should be a diff against it.

Chapter 10 · Contribute & learn

Now build your own

gase-recomp is meant to be read, forked and outgrown. Contributions are welcome — and so are entirely new recompilers for other machines that borrow its structure.

How we work

The repository follows a simple git flow. main only receives releases. develop is the integration branch. Every change lives on a feature/* or fix/* branch and lands in develop through a pull request, with CI green.

The build-your-own-recomp checklist

Nothing on this list is specific to the 68000. Swap the CPU and the hardware, and it is the plan for a recompiler of almost any classic machine. Tick them off as you go — the state stays in your browser.
