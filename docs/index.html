A pedagogic static recompiler · Sega Genesis / Mega Drive

ROM in.Native game out

gase-recomp reads the Motorola 68000 machine code of a cartridge you own and rewrites it, ahead of time, as native Rust that runs on the chips of the gase emulator. It started life in C and Python. This page tells how both were made — every step, explained so you can build one yourself.

01

Chapter 01 · The pitch

Three steps, zero game data

An emulator pretends to be a Mega Drive. gase-recomp does something different: it translates the game itself into a program — Rust today, C in its first draft — once, before it ever runs. What you get is a regular native executable — debuggable, profilable, portable.

The tool is deliberately small and heavily commented. It is not trying to be the fastest or the most compatible recompiler out there; it is trying to be the one you can read from end to end in a weekend and then reuse the ideas for another CPU.

  1. STEP 01

    Bring your ROM

    A dump of a cartridge you own: .bin, .md, .gen or interleaved .smd. The loader validates the header and the checksum.

  2. STEP 02

    Choose a platform

    The generated game runs inside gase's own frontends: a desktop window on Linux, macOS or Windows, or headless. Phones and the browser come next.

    • Desktop
    • Headless
    • Android · iOS · web next
  3. STEP 03

    Recompile

    gase-recomp disassembles, analyses and writes a Rust crate. cargo run --release builds a copy of gase that knows your game.

Two editions

gase-recomp was first written in C + Python: a Python generator and a C + SDL2 runtime. It now lives in Rust, on top of gase, a Mega Drive emulator by the same author.

The C draft stays in the repository as a teaching reference, and the chapters below quote both. Chapter 10 tells why the switch happened and what it changed.

Legal

Bring a ROM you own. gase-recomp ships no game data, no BIOS and no copyrighted assets — only the tool and a hand-written test ROM.

The generated code is a derivative of the game you fed it: keep it for yourself, do not redistribute it.

02

Chapter 02 · Strategy

Why static recompilation?

There are three ways to run old software on new hardware. They differ in one question: when does the old machine code get understood?

Emulation

At runtime, every instruction

An interpreter (or a JIT) fetches, decodes and executes each 68000 instruction while the game runs. Extremely general — self-modifying code, anything goes — but the work is repeated forever, and the program stays a black box.

Effort
Output
A virtual machine

Decompilation

By hand, over years

Humans rewrite the game in C, function by function, until it compiles back to a byte-identical ROM. The result is beautiful, readable source — and it costs thousands of hours per game.

Effort
Output
Human-quality source

Static recomp

Ahead of time, by a tool

A program translates the machine code into C or Rust mechanically, once. The CPU disappears into the host language; the hardware (video, sound, timers) is still emulated by a runtime library. You get native speed and a real program — without hand-writing it.

Effort
Output
Native, ugly but honest code

Static recompilation is not new. Projects such as N64Recomp (Nintendo 64) and XenonRecomp (Xbox 360), and many earlier experiments, showed that the approach scales to real games. gase-recomp applies the same idea to a much simpler machine — which is exactly why it makes a good classroom.

The hard parts are always the same, whatever the CPU: knowing where the code is, handling jumps you cannot predict, and keeping time consistent with hardware that expects interrupts at precise moments. The rest of this page tackles them one by one.

03

Chapter 03 · Loader

Anatomy of a Genesis ROM

A cartridge is just the bytes the CPU sees at address $000000. Learn to read its first 512 bytes and you know where every game begins.

The Mega Drive's main CPU is a Motorola 68000 at about 7.67 MHz: eight 32-bit data registers d0–d7, eight address registers a0–a7 (a7 is the stack pointer), a 24-bit address bus, and — important for every byte you will ever read — big-endian storage: the most significant byte comes first.

The exception vector table

The ROM opens with a table of 32-bit addresses. On power-up the 68000 loads its stack pointer from $000000 and its program counter from $000004. Interrupts and traps jump through the other entries. For a recompiler, this table is gold: it is the list of places where execution is guaranteed to start.

The Sega header at $100

Right after the vectors comes a fixed-layout ASCII header. The console name field must read SEGA MEGA DRIVE or SEGA GENESIS — later consoles' TMSS boot code actually refuses cartridges without SEGA there.

The checksum is a plain 16-bit sum of every big-endian word from $200 to the end of the ROM. It is a sanity check, not a security feature — but it tells you immediately whether your dump is intact.

Undoing the SMD interleave

Old copier devices (the "Super Magic Drive") saved ROMs in a strange layout: a 512-byte header, then 16 KiB blocks where the first 8 KiB hold all the odd bytes and the next 8 KiB all the even bytes. The loader detects it and weaves the bytes back into a flat image, so nothing downstream ever has to care.

Generic lesson: normalise inputs at the very edge of your pipeline. Every later stage assumes one canonical, flat, big-endian image.

Chapter 04 · Decoder

Reading 68000, one word at a time

Every 68000 instruction starts with one 16-bit opcode word. Its top four bits — the "line" — tell you which family you are in; the rest are packed fields.

Line 0 holds immediate operations and bit manipulation, lines 1–3 are MOVE (byte, long, word — yes, in that order), 4 is a grab bag (LEA, JSR, RTS, CLR…), 6 is branches, 7 is MOVEQ, 8/9/B/C/D are arithmetic and logic, E is shifts and rotates. Lines A and F are unassigned and trap.

Try it: pick an instruction and hover the fields.

000002043080  move.w d0,(a0)

00 · 11 (word) · 000 (dest reg) · 010 (dest mode (An)) · 000 (src mode Dn) · 000 (src reg).

Effective addressing modes

Most instructions name their operands with a 6-bit effective address: 3 bits of mode, 3 bits of register. Mode 7 is an escape hatch whose register field selects the "special" modes. Some modes need extension words after the opcode — which is why instruction length varies from 2 to 10 bytes, and why you cannot decode a 68000 program by just stepping two bytes at a time.

The code-versus-data problem

Here is the catch that shapes the whole project. A ROM is a soup of code, graphics, music, level maps and lookup tables, with nothing marking which is which. A tile of pixels decodes happily into nonsense instructions. A linear sweep from $200 to the end would "disassemble" megabytes of art.

So the decoder never chooses where to look. It is a pure function — decode(rom, address) → instruction — and the decision of which addresses are code belongs to the next stage.

Being pure also makes it easy to check exhaustively. The Rust decoder (crates/recomp/src/m68k) is compared with gase's on every one of the 65,536 possible opcode words: same validity, same length, same operands.

05

Chapter 05 · Analysis

Finding the code by following it

If we cannot tell code from data by looking, we tell it by following: start where the CPU is guaranteed to start, and go wherever it can go.

This is recursive descent. The work list is seeded with the reset vector, the interrupt vectors and the TRAP vectors. For each entry, the analyser decodes instructions one after the other, and at each branch it adds the target(s) to the list. A function is an entry point plus every instruction reachable from it through branches (BRA, Bcc, DBcc, JMP to a known label). A call — BSR or JSR — does not extend the current function: it discovers a new one.

The wall: indirect jumps

Games love jump tables. A state machine reads an index, scales it, loads an address from a table and does jmp (a0). The analyser sees a0 but has no idea what it will hold at runtime. Some patterns can be pattern-matched (a d8(PC,Xn) table right after the jump, for instance), but in general this cannot be solved statically — it is a cousin of the halting problem.

gase-recomp does not pretend otherwise. It turns the problem into a workflow, which is the single most important idea to take away from this page:

  1. Recompile what you can see.Recursive descent from the vectors, plus any entry list you provide.
  2. Run the game.Every indirect jump goes through a dispatcher that looks the target up in the recompiled code.
  3. Log what is missing — and keep playing.An unknown target is appended to gase_missing.txt. The C draft stopped there; the Rust edition lets gase's interpreter run it until the code is back on known ground.
  4. Feed it back.Re-run gase-recomp recomp: it picks up gase_missing.txt by itself. Coverage grows with each play session, until it converges.

A real session on the project's test ROM: a jsr (a0) the analysis could not follow ran on the interpreter, was logged, and became the fifth function on the next pass. Static analysis proposes, the running program disposes — every serious recompiler ends up with some version of this loop.

Chapter 06 · Codegen

Every instruction becomes a little C

The code generator is almost boring, on purpose: each 68000 instruction is replaced by a small block of code that does exactly what the CPU would have done, then charges the right number of cycles.

This chapter reads the C first draft, because C's goto maps onto 68000 branches one to one. The Rust edition emits the same blocks — cx.cycles += 8 instead of CYC(8), cx.logic(v, 2) instead of op_logic(v, 2) — and handles branches differently, as chapter 10 shows.

D(n) and A(n) are the emulated registers, W16 writes a big-endian word through the memory bus, op_logic sets the N and Z flags and clears V and C exactly as MOVE does, and CYC(8) adds the instruction's cycle cost to the clock. The original address and disassembly stay in a comment, so the output remains a readable map back to the ROM.

The CPU is a struct

The machine state is a plain C struct. Flags are stored unpacked — one byte each — because testing gase_cpu.z is much cheaper than masking a status register on every branch; the real SR is only rebuilt when the game reads it.

Flags come from tiny helpers — op_add, op_sub, op_logic… — declared static inline (in Rust, #[inline(always)] methods on Cx). The compiler inlines them, and when a flag is overwritten before anyone reads it, the optimiser simply deletes the dead computation. You write the obvious thing and let the compiler make it fast.

Branches, calls and returns

Inside a function, a branch is a goto to a label named after its address. A call — BSR/JSR — pushes the 68000 return address on the emulated stack, exactly like the real CPU, and then makes a real C call. RTS pops the address into gase_cpu.pc and returns.

Why check gase_cpu.pc after the call? Because 68000 code is free to cheat: a routine can drop its return address and push another one, or a game can switch threads by swapping stacks. If the address that came back is not the one we expected, the C call stack no longer matches the 68000 stack. The function then unwinds to a top-level trampoline, which looks up the real target in the dispatch table and jumps there. When that target is in the middle of a function — just after a call site — the function's resume points (a small switch at its entry) let it be re-entered right at that label.

Generic lesson: map the source machine's control flow onto the host's whenever it is safe, and keep a slow but correct escape hatch for when it is not. (In Rust, that escape hatch became the normal path — see chapter 10.)

Chapter 07 · Runtime

The CPU is gone. The console is not.

Recompiled code still writes to $C00000 expecting a video chip to be there. The runtime plays the role of everything that is not the 68000 — a small C library in the first draft, gase's own chips in the Rust edition.

  1. $000000Cartridge ROM — up to 4 MiBRead directly from a byte array; inlined fast path.
  2. $400000Unused / expansion
  3. $A00000Z80 address space8 KiB sound RAM and the YM2612, shared with the sound CPU.
  4. $A10000I/OVersion register, controller ports, Z80 bus request ($A11100), TMSS ($A14000).
  5. $C00000VDP + PSG portsData port, control port, H/V counter; the PSG lives at $C00011.
  6. $FF0000Work RAM — 64 KiBMirrored from $E00000. Inlined fast path.

The video display processor

The VDP owns 64 KiB of VRAM holding 8×8 tiles and the maps that arrange them into two scrolling planes, A and B, plus a fixed window plane and up to 80 sprites. Colours live in CRAM: four palettes of sixteen 9-bit colours (that is why every colour on this page is a legal Mega Drive colour). Games feed it through a two-word command protocol on the control port and bulk-copy data with DMA. Both runtimes render one scanline at a time, so mid-frame tricks — changing scroll or palette from an HBlank interrupt — keep working.

Sound is the SN76489 PSG — three square-wave channels and one noise channel — plus the YM2612 FM chip driven by the Z80 (the C draft stops at the PSG; gase has both). Controllers are read through the I/O ports with the classic TH-line multiplexing.

Interrupts in an ahead-of-time world

Here is the subtle part. An interpreter can check for interrupts between any two instructions. Our recompiled code runs straight C — so who interrupts it? Answer: cycles and poll points.

VBLANK · LINES 224–261
IRQ 6
Count
Every instruction adds its cost: CYC(n) in C, cx.cycles += n in Rust. About 488 68000 cycles make one NTSC scanline; 262 lines make a frame.
Poll
On every backward branch — every loop — the generated code calls POLL(addr) / cx.poll(addr). It is one compare in the common case.
Fire
When a scanline has elapsed, the scheduler runs the VDP for that line. At line 224 it raises the level 6 VBlank interrupt: push PC and SR, call the handler from the vector at $78, resume at the loop head on RTE.

Since every loop polls, and straight-line code is short, an interrupt is never late by more than a few dozen cycles — well under a scanline. That is the trick that lets a program compiled ahead of time still behave like it lives inside a console.

Chapter 08 · Shells

One game, many shells

A recompiled game should not care where it runs. Everything platform-specific lives in a thin shell: a window, a texture, an audio callback, input.

In the Rust edition, the shell is not even ours: it is gase's. The generated program registers its recompiled code, then runs gase, whose frontends call Genesis::run_frame() once per frame and read back the picture and the audio — the very call they make for the interpreter. Chapter 10 tells how. Here is where things honestly stand:

Desktop

gase's SDL shell · today

Linux, macOS and Windows. cargo run --release opens gase's window: menus, save states with previews, rewind, gamepads, settings. --headless runs frames without a window and can dump a screenshot — handy in CI.

Android · iOS

gase-mobile · next

gase's app shells, touch controls included, already run that same shell. What is missing is small: SDL_main in gase-mobile must let a game crate register its code before the shell starts. (The C draft's Gradle and Xcode templates were never built on a real device.)

Web

gase-web · next

A runtime without a line of unsafe, on chips gase already runs in the browser: WebAssembly is the natural route. Same follow-up: gase-web's wasm exports must give a game crate the chance to register first.

info prints the header, vectors and checksum status; disasm shows what the analysis found; recomp writes a Cargo crate: src/main.rs registers the code and runs gase, the generated code lives under src/recomp/, and rom.bin opens at start. --platform headless leaves SDL2 out. All of gase's options apply (--help). The C draft's equivalent is still there: python -m gase recomp … --platform desktop|android|ios.

Chapter 09 · Verification

Trust, but diff

A recompiler is wrong in silent ways: one flag computed incorrectly and a game takes the wrong branch ten minutes later. You cannot debug that by playing. You need a referee.

For the C first draft, the referee is Musashi, a mature and widely used 68000 emulator written in C. The technique is differential testing: generate random but valid instruction sequences, run them through both Musashi and the recompiled C from the same starting state, and compare everything afterwards. (The Rust edition swapped in a sharper referee — and it found bugs this one had missed. See chapter 10.)

Generate

Random opcodes, operands and sizes, a random register file, a few random bytes of RAM. Seeded, so every failure is reproducible.

Reference

Musashi interprets the sequence.

Under test

gase-recomp recompiles it to C, which is compiled and run.

Compare

d0–d7, a0–a7, X N Z V C, SR, a CRC32 of the 64 KiB of RAM (exception stack frames included). Any mismatch prints the seed and the instruction.

Random tests find the bugs you did not imagine. For the ones you did, there is a small hand-assembled test ROM: a real cartridge image, written from scratch for the project, that exercises the vectors, the VDP, interrupts and jump tables — and is legal to ship. Everything runs on GitHub Actions for every pull request: unit tests, the differential suite, and a full recompile-and-build of the test ROM. The Rust edition has the same pair: crates/difftest and crates/e2e.

Generic lesson: if a mature reference implementation exists for your CPU, your first test harness should be a diff against it.

Chapter 10 · Second edition

The Rust turn

The C version worked, and taught a lot. Then the project changed language — not for fashion, but because a whole Mega Drive, minus one chip, was already waiting in Rust.

That console is gase, the author's own Mega Drive emulator: pedagogic like this project, one crate per chip, #![forbid(unsafe_code)], CPU cores validated against about 2.6 million hardware test vectors, with desktop, Android, iOS and web frontends. A recompiler replaces the 68000 and nothing else. So the Rust edition — the crates/ workspace — recompiles the 68000 and borrows everything else from gase.

Reuse every chip but one

Rewriting a VDP with FIFO and DMA timing, a YM2612, a Z80 and the cartridge mappers for a recompiler would have meant writing a second, worse emulator. Instead, gase's Hardware struct — its whole memory map — already implements the 68000 Bus trait its interpreter talks to. Recompiled code plugs into that very same bus. At first gase needed zero changes: it is a git dependency pinned to one commit. Later it gained exactly one module, so it could take recompiled games into its own frontends — the end of this chapter tells that story.

No goto? Then a state machine

The C draft turned every branch into a goto. Rust has none. So each 68000 function becomes a loop around a match on the address of the next block — a run of instructions with no label inside. A branch is pc = TARGET; continue, which LLVM compiles straight back into a direct jump. Any address that is not one of the function's blocks falls into the _ arm and goes back to the dispatcher. The native stack is only a cache

A side effect turned out to be the best idea of the rewrite. Since a function starts with match pc, it can be entered at any of its blocks, not only at the top. The C draft needed resume points and a trampoline for that rare case; here it is the normal case. So the native Rust call stack does not have to mirror the 68000's: it is just a cache of the emulated stack, which lives in work RAM like on the real console.

And a cache can be thrown away. When a poll point notices that the frame is over, the runtime raises an unwinding flag: every function returns, all the way up to run_frame, leaving cx.pc on the block to resume. The next frame simply dispatches cx.pc again. The game is now frame-steppable — run_frame runs exactly one frame and returns, which is the shape every frontend (SDL window, phone, browser) expects. Keep this in mind: it is what later let the game move into gase's own frontends.

call pushes the real 68000 return address, then makes a native call; returned checks that the game came back where expected — and says "return too" while unwinding.

Code the analysis missed keeps running

In the C draft, reaching code that had not been recompiled stopped the game: the address went to gase_missing.txt and you had to recompile before going further. The Rust runtime has a better answer at hand: gase's own 68000 interpreter, on the same bus. dispatch runs the recompiled code if there is any, and otherwise hands the CPU state to the interpreter, which steps until execution lands on a recompiled block again. The address is still logged, so the next gase-recomp recomp turns it into a function — the coverage feedback loop of chapter 05, without the crash.

The scheduler, turned inside out

gase's own run_frame drives its 68000 one instruction at a time and handles scanline events in between. A recompiler cannot work that way: the code runs freely. So the roles are flipped. At each poll point (every backward branch) and before every I/O access, the recompiled code tells the machine how many cycles it has used, and the machine catches up: it runs the scanline state machine, the Z80 and the audio to that moment. Time is counted in master clock ticks — the 68000 runs at master / 7, the Z80 at master / 15, a line lasts 3420 ticks, HBlank starts at 2650 and, on the first blank line, VBlank fires at 770.

CPU cycles × 7 = master ticks. The return value is the next deadline, so cx.poll stays a single compare until something is due. gase-recomp first wrote this inverted scheduler itself, as GenesisMachine; it now lives in gase, as External — see below.

The price: compile time

Rust has one real risk for static recompilation: rustc on huge generated functions. To measure it before betting on it, an example program builds a synthetic ROM full of random valid code, the size of a large Mega Drive game:

  • 157,00068000 instructions
  • 985,000lines of Rust
  • 41 MBof generated source
  • 0.8 sto generate
  • 10 minrelease build, 4-core CPU

Generating is instant; compiling is the bill — about ten minutes on a modest 4-core machine for this deliberately heavy random code (a real 2.2 MB game later took about five, see below), paid once per game rather than every frame. Measuring where it goes was the instructive part: rustc’s own front end (type and borrow checking) takes a few seconds; LLVM takes the rest, and its cost grows faster than the code. Long functions full of loads and stores are what hurt: the same 30,000 instructions built in 146 s as long routines and in 50 s as short ones, while the optimisation level barely mattered (135 s at opt-level = 1). So the generator now shapes its output for the compiler:

  • Many small filesFunctions are spread over part_NNN.rs modules, so rustc never sees one giant file.in place
  • Fast dev builds, fast dependenciesopt-level = 1 for the game code, opt-level = 3 for gase's chips: play-testable without a full release build.in place
  • Parallel code generationcodegen-units = 16 in release lets LLVM work on many parts at once.in place
  • Short blocks, chunked functionsStraight-line runs are cut every 24 instructions, and big 68000 routines become several #[inline(never)] chunk functions of about 48 instructions that hand the next pc back to a small match (146 s → 107 s on the 30k test). --chunk and --max-block let you experiment.in place
  • Lean inliningOnly the frequent flag helpers are inlined; a memory access is a call into the console (whose work-RAM fast path is inlined on gase's side), and BCD, divisions and rotates through X stay out of line, keeping each instruction’s IR small.in place

Home at last: inside gase's frontends

Until then, the Rust edition carried its own little shell: an SDL window and a headless runner, inside the runtime crate. They worked — with no menus, no gamepads, no save states. gase had all of that already, on every platform. Writing it a second time would have been the VDP mistake all over again. So the recompiled game moved in with gase.

The inverted scheduler — the one gase-recomp had written for itself, as GenesisMachine — moved into gase, where it belongs, as an external-CPU mode: gase_core::system::external. Its contract is one trait, and External is the console as an external 68000 sees it for one frame: the same Bus as the interpreter's, plus set_clock, catch_up and frame_done. On gase's side, the whole external path of Genesis::run_frame is about twenty-five lines:

Between frames, the CPU is gase's

Here is what makes the integration clean. Each frame, the recompiled CPU loads its registers from gase's M68k — the interpreter's own state — runs, and stores them back. Between two frames, the 68000 is gase's, exactly as if the interpreter had run. So everything gase built around that struct keeps working without knowing anything changed: save states, rewind, the debugger's register views. And the very same M68k is the interpreter fallback for code the analysis missed.

It only works because of the cache idea above. A recompiler whose native stack mirrored the 68000's could never hand its state over: part of it would be return addresses buried in Rust frames. Ours unwinds at every frame end, so when run_frame returns, nothing is left anywhere but in the registers and in RAM — exactly what gase already saves.

The runtime crate came out of it about 600 lines lighter: its own scheduler, its game wrapper and both frontends are gone. Cx<'a> now simply borrows the console as &mut dyn Machine for the length of one frame. No generics in the generated code: each memory access goes through an indirect call, which is noise at 7.67 MHz — and it keeps every generated function smaller for LLVM, whose bill we just read.

One registry, keyed by checksum

How does gase know which ROM is recompiled? The generated program calls gase_recomp_runtime::register(ROM_CRC32, recomp::cpu) first thing in main, then hands over to gase::run_command_line(args) — gase's whole main, moved into its library for the purpose. From then on, any console gase creates for that ROM, matched by its CRC-32, runs the recompiled code; any other ROM runs on the interpreter as usual. This is the main.rs gase-recomp writes, minus a helper that finds rom.bin:

So the generated game binary is gase — window, menus, save states with previews, rewind, gamepads, touch controls, settings — with one more CPU. Open another cartridge from its menu and that one simply runs on the interpreter.

Gotcha · one gase-core

The registry is a static inside gase-core. If the game and the runtime asked for gase at two different revisions, Cargo would happily build two copies of gase-core: the game would register into one, gase's frontend would create its consoles from the other, and the game would silently run on the interpreter.

So the generated Cargo.toml pins gase at exactly the runtime's revision, and a unit test fails as soon as the generator's GASE_REV and the workspace drift apart.

Testing an inverted scheduler

Moving the scheduler into gase raised the obvious question: is External really the same console as Genesis::run_frame, just turned inside out? gase answers with the CPU it trusts most — its own interpreter. Its test drives the interpreter through External, with a ten-line ExternalCpu that steps one instruction at a time, and checks that work RAM, Z80 RAM, the picture and the registers match the normal scheduler exactly: with interrupts, with the Z80 running alongside, and with a 68000→VDP DMA that must freeze the CPU for just as long. Save states round-trip too, and registration picks consoles by checksum.

Generic lesson: to test an inverted scheduler, run your known-good CPU through it. Any difference is then the scheduler's fault, never the CPU's.

Proof, on screen

On the project's test ROM, gase's headless frontend now introduces the game in its own words — and runs it at around 1,800 frames per second. An end-to-end test (crates/e2e) checks that after 60 frames the recompiled game shows the same picture and holds the same RAM as gase's interpreter, and that save states round-trip.

First real game: hashbug

The test ROM proves the mechanics; a real game proves the point. The first one was hashbug, a Mega Drive homebrew of 2.2 MB, recompiled by the author on their own machine:

  • 2.2 MBhomebrew ROM

  • ≈ 5 minrelease build

One recompilation was enough to play it, and the picture matched the same ROM running on gase's interpreter. The release build took a good five minutes — half the ten minutes of the synthetic benchmark above, which is no surprise: real code is mostly moves, compares and branches, far lighter than random instructions full of BCD, divisions and rotates through X.

Generic lesson: benchmark with a pessimistic synthetic workload to decide whether an approach can work at all, then let the first real program tell you how it actually behaves.

Second game: Aladdin, and an estimate that was not enough

Then a commercial game: Aladdin, the 1993 Virgin platformer, famous for its hand-drawn animation, which it streams into video memory frame after frame. One pass of recomp, a release build in under four minutes, and the game was fully playable. Almost right: the genie-lamp health meter sometimes showed pieces of a guard's sword instead of smoke, and now and then a column of the background turned into a jumble of tiles. The same ROM on gase's interpreter: clean. Sonic 1, recompiled the same way: clean on its first two levels.

  • 1 passof gase-recomp recomp
  • < 4 minrelease build
  • playablefrom start to end of level
  • ≈ 11 %too fast: our cycle estimate, measured

When only the CPU is different and the picture breaks, suspect time. Recompiled code has no clock: each instruction adds its cycle count to cx.cycles, and that number decides when the rest of the console catches up — when a scanline is drawn, when VBlank fires, when the game's DMA uploads land. Ours was an estimate (two cycles per word, a few more per memory operand), written early on, above a comment that said “we only need about right”. Measured against gase's 68000 on every opcode, it was about right on average and wrong almost everywhere: moveq 6 instead of 4, lea 17 instead of 8, addq.l 13 instead of 19, about 11 % too fast overall. Sonic forgives that. Aladdin, which fills VBlank with graphics uploads to the last cycle, does not.

The fix follows the rule of this whole project: don't model what you can measure. The generator now runs every instruction once, with its real extension words, on gase's interpreter in a little sandbox, and keeps the cycle count it reports. The few timings that depend on run-time values are split into a measured part and a part the generated code adds:

And the differential test got one more column. It already compared registers, flags and memory after thousands of random instruction sequences; it now compares the number of cycles too, and it must be exactly the interpreter's. The first run of that test found what the estimate had hidden: CHK's two trap paths, the extra 2 cycles of BSET/BCLR/BCHG on bits 16–31, an immediate divisor counted twice. Each is a line in the generator now, and the test passes on every seed we tried.

Generic lesson: “about right” is a debt. Timing errors don't crash anything; they move work across a deadline the game relies on, and only the most demanding program will show you. Turn the estimate into a measurement, and put the measurement under test.

The second round: time that ran for free

Level 1 was now clean, but one situation still broke the picture: getting knocked out in Agrabah while grabbing an item. The HUD tiles were wrong again, and they stayed wrong into the desert level. The cause sat in the runtime, not in the generator. A 68000-to-VDP DMA freezes the CPU for the whole transfer, and the VDP's FIFO and the Z80 bus make it wait too. gase added that time to the console's clock at once, but the recompiled code only took it into account at the next scheduler event. Until then, the instructions that followed ran for free, overlapping the wait. With a game that does big DMAs, that is thousands of extra cycles per frame. The respawn reloads graphics with large transfers, so that is where it showed.

The fix is two lines: after every access to the Z80 area, the I/O ports or the VDP, the CPU catches up with the console's clock right away, exactly as gase's interpreter does. A unit test with a mock console whose VDP makes every write wait 100 cycles fails without it. After that change, the knockout no longer broke anything.

For the next time, the generated game also got a bisection switch: GASE_RECOMP_INTERPRET=all, or address ranges such as 0-0xFFFFF, runs that code on gase's interpreter even though it was recompiled. If a bug disappears, the faulty routine is in the range; halve it and try again. About twenty tries, starting from a save state, find one routine in a 2 MB ROM.

Generic lesson: a recompiled CPU still lives inside a machine that makes it wait. Count waits when they happen, not when it suits the scheduler. And ship a way to bisect: the bugs that matter show up on hardware and games you don't have.

In your pocket: the same game on Android and iOS

The original promise was “bring your ROM, pick a platform”. gase already ran on phones; what was missing was a way for a game to be the app. On a phone there is no main: the system starts the app through its own framework, and SDL then calls one C function, SDL_main. gase's phone crate exported that function itself. So the change in gase is a switch: gase-mobile got an sdl-main feature, on by default, and a run_game function. A game crate turns the feature off and exports its own SDL_main.

Every generated game now carries a second, tiny crate, mobile/, in the same workspace. It reuses src/recomp/ through a #[path] module, so there is still only one copy of the game's code:

  • Proved by CIgase-recomp's CI recompiles the hand-made test ROM, builds its APK with gase's own Android project, and checks the package name, the label, and that libmain.so exports the game's SDL_main.in place

Generic lesson: when a framework owns the entry point, make the entry point replaceable instead of copying the framework. A feature flag and one function in gase were enough; every game reuses the rest: touch controls, menus, save states, the Gradle and Xcode projects.

Pick a ROM, press Build, get an APK

Phone builds worked, but only for someone who already knew Gradle, the NDK and where gase lives. The last step was a window for everyone else: gase-recomp studio (cargo run --release -p gase-recomp-studio). It has three cards: the ROM (title, size, CRC-32, checksum), the app (its name and identifier, the processors to build for) and Build. On the right, a list of what the computer needs, checked live: Rust and its Android target, git, Java, CMake, the SDK, the NDK. (Not Gradle: gase's Android project brings its own, a Gradle wrapper pinned to the version its Android plugin needs, so whatever Gradle a computer has does not matter.) When a fix is a single command, such as rustup target add … or sdkmanager --install "ndk;…", a button runs it.

The window is only a layer. Everything the button does lives in pipeline.rs, which reports progress as events on a channel: recompile the ROM with the generator library, clone gase once into a cache at the pinned revision, run its Gradle project with -PgaseCrate, copy the APK next to the project. The same pipeline runs without a window, gase-recomp-studio --cli game.md, and that is how CI builds the test ROM's APK on every pull request. The button is tested even though nobody clicks it.

The studio builds for this computer too. Choose This computer and the button becomes Build the game: recompile, then cargo build --release on the generated crate. A Play button starts the result, which is gase itself with the game's code compiled in. This is the build gase's own pause menu opens with Recompile to native… (gase-recomp-studio --desktop game.md).

Generic lesson: put the work in a library and the window on top. The GUI stays small enough to read, and everything it does can be scripted and tested.

Recompiling while the game runs: a JIT

Everything so far happens before the game runs: the whole ROM is translated, rustc and LLVM compile it, and you get one program per game. A phone cannot do that; it has no compiler. A JIT (just-in-time compiler, or dynamic recompiler) flips it around. The first time the 68000 reaches an address, it decodes the code there, writes machine code for it into memory, and jumps to it. The next time, the code is already there. Nothing is built in advance, so it works for any ROM.

Most of the pieces already existed. crates/jit reuses the generator's decoder and its measured timings, and the console seen as a Machine. What is new is small and pedagogical:

  • A tiny IRir.rs turns a block (straight code up to a branch) into operations: Move, Alu, Lea, Branch, Dbcc… Anything not translated yet becomes Interpret: run that one instruction on gase's interpreter, registers handed over and back. The JIT is correct for every game from the first day, and native coverage grows one family at a time.in place
  • x86-64 machine codex64.rs writes the code with dynasm. The 68000's flags map onto x86's: after an add of the same width, x86's carry, overflow, sign and zero are the 68000's C, V, N and Z. Memory goes through Rust helpers that tell the console the time, as the runtime does.in place
  • RegionsThe first version compiled one block at a time and came back to the engine after each: 1.4× the interpreter. Compiling a block together with the blocks its branches reach turns a loop into a real machine-code loop that runs until the console needs attention. That brought it to 10.6×.in place
  • Tested like the restA difftest runs random snippets on the JIT and on gase's interpreter and compares registers, flags, memory and cycles; an end-to-end test plays the test ROM on a gase console with the JIT, frame for frame against the interpreter.in place

Both runs end with the same registers, the same memory and the same number of cycles as the interpreter; the benchmark checks it. Static recompilation remains the better choice when you can build ahead: it sees the whole program and lets LLVM optimise it. The JIT is the answer when you cannot, on a phone for example. That is the next step: gase on Android with the JIT for any ROM. (iOS forbids apps to write machine code, so there gase stays with its interpreter.)

Phones run AArch64, so the JIT got a second backend, a64.rs, from the same IR. Two differences make it instructive. First, AArch64 computes flags only on 32 or 64 bits: a byte add is done on both operands shifted left by 24, so the byte sits at the top of the register, and the 32-bit carry, overflow, sign and zero are exactly the byte's. Second, ARM's carry after a subtraction means no borrow, the opposite of the 68000, so sub and cmp read the "carry clear" condition. The same difftest runs the ARM64 code under qemu, on every pull request, and it passed the first time.

Then the JIT went into gase itself. gase lets a game register its own CPU for its ROM's checksum; a new external::register_any registers one for every ROM. crates/jit-app calls it and starts gase: gase-jit game.md on a desktop, where gase's info line reads 68000: JIT (x86-64), and an Android app, "gase JIT", whose SDL_main does the same before handing over to gase's phone shell. Any ROM opened in it, from the menus or with "Open with", runs on machine code written while it plays. The test ROM's picture after 120 frames is byte-identical to the interpreter's, and CI builds the APK with gase's own Android project on every pull request.

Generic lesson: start a JIT with an escape hatch. If every instruction can fall back to a trusted interpreter, the JIT is correct before it is fast, and each new native instruction is a small change checked by the same differential test.

Make an app from the phone

"gase JIT" plays any game on a phone, but a phone still cannot make an app of one: rustc and Gradle do not run there. The computer that can is usually in the same room, though. So the phone asks it. In gase JIT's pause menu, Make an app of this game… looks for the studio on the local network, sends it the ROM, follows the build with toasts, downloads the APK and hands it to Android's installer. Nothing is typed on the phone, no account or token is needed, and the ROM never leaves the network.

The studio answers only once Phone builds is switched on, and builds only what someone accepts on the computer:

Three small pieces make it work, each one tested on its own. crates/remote is the protocol, a few hundred lines on the standard library's sockets, with round-trip tests on real ports. gase got a hook: an app's SDL_main passes Hooks { recompile } to gase_mobile::run_with, and the pause menu shows the entry. The hook runs on a thread and reports through Notices, a toast queue that the main loop empties each frame. Last, gase_mobile::install_apk writes the APK to the app's folder and sends a message to the Java activity. It opens a PackageInstaller session, and Android asks the user to confirm. Only an app built with -PgasePhoneBuilds asks for the two permissions this needs (network and installing apps); gase's own app still asks for none, and CI checks both. The phone's half is tested on a desktop against a real studio server: the same toasts, the same APK.

Generic lesson: when a device cannot do the work, ask a machine nearby that can, but keep a person in the loop. Here that is one Accept click on the computer and the system's own install prompt on the phone.

Two implementations, one lesson

The C + Python version stays in the repository (gase/, runtime/, tests/) as the first draft: shorter, closer to the classic recompilers, and still the clearest way into chapters 03 to 09. The Rust edition is where the project goes. Reading both side by side is the point: the pipeline — loader, decoder, analysis, codegen, runtime, feedback loop, differential tests — did not change at all. Only the host language and the shoulders it stands on did.

Generic lesson: the architecture of a recompiler outlives its implementation language. Keep the stages small and you can rewrite any of them.

Chapter 11 · Contribute & learn

Now build your own

gase-recomp is meant to be read, forked and outgrown. Contributions are welcome — and so are entirely new recompilers for other machines that borrow its structure.

How we work

The repository follows a simple git flow. main only receives releases. develop is the integration branch. Every change lives on a feature/* or fix/* branch and lands in develop through a pull request, with CI green.

The build-your-own-recomp checklist

Nothing on this list is specific to the 68000. Swap the CPU and the hardware, and it is the plan for a recompiler of almost any classic machine. Tick them off as you go — the state stays in your browser.
